# LandHere — Production Deployment Runbook

_Written 2026-08-16 for `feat/pro-iap`._

**Nothing here has been executed.** No infrastructure exists, no account has
been created, and no cost has been incurred. This is the procedure to follow,
written from the code and config in this repository — not a record of a
deployment that happened.

Platform: **Render**, because `render.yaml`, `Dockerfile` and `start.sh` are
already written for it and it provides managed PostgreSQL and a managed Key
Value (Redis-compatible) instance in one place. `railway.toml` is present as an
alternative; this runbook covers Render.

---

## 0. Before you start

| You need | Why |
|---|---|
| A Render account with a payment method | Managed Postgres and Key Value are paid |
| Apple's root CA in `vendor/apple-root-ca/` | Purchase verification is 503 without it — see that directory's README |
| The numeric App Store Connect app id | Required to verify **Production** purchases |
| A decision on the API hostname | It sets `CORS_ALLOW_ORIGINS` and the mobile build's `EXPO_PUBLIC_API_URL` |

**Recurring cost.** Render charges for the web service, the Postgres instance
and the Key Value instance separately, and Apple charges $99/yr for the
Developer Program. Plan names and prices change; read Render's current pricing
page and total it yourself before provisioning. This file deliberately does not
quote figures it cannot keep accurate.

## 1. Provision

1. Push this branch to a Git remote Render can read.
2. Render Dashboard → **Blueprints** → **New Blueprint Instance** → point it at
   the repository. It reads `render.yaml` and proposes three resources:
   `landhere-api` (web), `landhere-db` (PostgreSQL), `landhere-cache` (Key Value).
3. Confirm the **database plan is not the free tier**. Free PostgreSQL instances
   are deleted after a trial window, which would take production data with them.
   `render.yaml` specifies a paid plan; verify the name is still current.
4. Apply. The first deploy will fail its health check until step 2 is done —
   that is expected, and it is the fail-closed config guard doing its job.

## 2. Set the variables Render cannot infer

In the `landhere-api` service → **Environment**. Everything marked `sync: false`
in `render.yaml` must be filled:

| Variable | Value | Notes |
|---|---|---|
| `CORS_ALLOW_ORIGINS` | your real origin, e.g. `https://api.landhere.app` | Boot **fails** on `*` or empty |
| `UNSPLASH_ACCESS_KEY` | the **rotated** key | Server-side only; never `EXPO_PUBLIC_` |
| `APPLE_APP_APPLE_ID` | numeric id from App Store Connect | Without it, Production purchases cannot be verified |
| `APPLE_ACCEPT_SANDBOX` | `true` while TestFlight testing, `false` for public release | Sandbox acceptance in production hands out free Pro |

`SECRET_KEY` is generated by Render. `DATABASE_URL` and `REDIS_URL` are wired
from the two data services by `render.yaml`.

**Never paste a secret into this file, into `render.yaml`, or into a commit.**
`.env` is gitignored; keep it that way.

### What fails closed, and why that is the point

With `ENV=production`, boot **raises** on a placeholder `SECRET_KEY`, on
wildcard or empty `CORS_ALLOW_ORIGINS`, on a localhost or placeholder
`DATABASE_URL`, and on `TRUST_PROXY_HEADERS=true` with `TRUSTED_PROXY_HOPS < 1`.
A deploy that crashes is recoverable. A live service with wildcard CORS and a
dev signing key is not.

## 3. Migrate

Migrations run automatically at container boot: `start.sh` executes
`alembic upgrade head` under `set -e`, so a failed migration **aborts startup**
rather than serving a half-migrated schema.

Watch the deploy log for the final revision:

```
Running upgrade e5f7a9b1c3d5 -> f6a8b0c2d4e6, add_purchase_notifications
```

That is head as of this branch — **11 revisions**. Verified locally against
PostgreSQL 18.4: `upgrade head`, `downgrade base`, re-upgrade and re-seed all
exit 0. Note that a managed instance may differ in extension availability and
permissions from a local one; the first deploy is the real test.

## 4. Seed — once, and only the launch data

```bash
python -m app.core.seed
```

Run it from a Render Shell on the web service. It is idempotent for countries
and inserts the three live corridors only:

```
22 countries · 15 IN→US · 12 IN→CA · 14 IN→UK
```

Do **not** run the unverified-corridor seeds (`seed_in_au_draft`). Rankings data
is separate and optional at launch: `ingest_scorecard` → `ingest_openalex` →
`compute_scores`, in that order, and only `has_full_score` schools are served.

## 5. Verify from outside your network

```bash
curl -i https://YOUR-API-ORIGIN/health/ready     # expect 200 {"status":"ok"}
curl -i https://YOUR-API-ORIGIN/health/live      # expect 200
curl -i https://YOUR-API-ORIGIN/docs             # expect 404 — disabled in production
curl -i https://YOUR-API-ORIGIN/info/journey?destination=US&origin=IN
#   expect 200, pro_required: true, and only the two free phases
```

The last one is the gate check that matters: an anonymous caller must not
receive `visa_process` steps. If they do, the deploy is serving content it
should be withholding.

Then confirm purchase verification is configured rather than silently 503:

```bash
curl -i -X POST https://YOUR-API-ORIGIN/purchases/notifications \
  -H 'Content-Type: application/json' -d '{"signedPayload":"not-a-real-jws"}'
#   expect 400  (verification ran and rejected it)
#   a 503 means APPLE_ROOT_CA_DIR / APPLE_APP_APPLE_ID are not set
```

## 6. App Store Connect: notification URL

App Store Connect → your app → **App Information** → **App Store Server
Notifications**. Set **Version 2**:

- Production Server URL: `https://YOUR-API-ORIGIN/purchases/notifications`
- Sandbox Server URL: the same path (same server, unless you run a separate one)

Use "Request a Test Notification" to confirm delivery. The endpoint accepts a
`TEST` notification and acts on nothing; a 200 means the URL and the signature
verification are both working.

Until this is configured, a refund only reaches us when the user next restores.

## 7. Backups

```bash
# BEFORE every deploy that includes a migration.
pg_dump "$DATABASE_URL" --format=custom --file=landhere-$(date +%Y%m%d-%H%M).dump
```

Enable Render's managed daily backups on the Postgres instance as well, but keep
taking your own pre-deploy dump: managed snapshots are point-in-time, and you
want a known-good artifact tied to a specific release.

### Restore rehearsal — do this before you have users

A backup you have never restored is not a backup.

```bash
createdb landhere_restore_test
pg_restore --dbname=landhere_restore_test --clean --if-exists landhere-YYYYMMDD-HHMM.dump

# Prove it actually restored, rather than exiting 0 with an empty schema:
psql landhere_restore_test -c "select count(*) from countries;"    # expect 22
psql landhere_restore_test -c "select count(*) from info_steps;"   # expect 41
psql landhere_restore_test -c "select count(*) from purchases;"    # expect your real count
psql landhere_restore_test -c "\d purchases"                       # expect the UNIQUE constraint
dropdb landhere_restore_test
```

That last check matters more than it looks: the UNIQUE constraint on
`original_transaction_id` **is** the entitlement model. A restore that loses it
would let one purchase entitle several accounts.

## 8. Rollback

**Application first, schema second.** Old code against a new schema usually
survives; new code against an old schema does not.

1. **Redeploy the previous image.** Render keeps prior deploys and offers
   one-click rollback. Do this first; do not start editing schema under pressure.
2. If — and only if — the schema must also go back:

```bash
pg_dump ...                      # ALWAYS first: downgrades that drop columns
                                 # destroy data the dump is the only copy of
alembic current                  # what the DB thinks it is
alembic history --verbose        # the chain
alembic downgrade -1             # step back exactly one revision
alembic current                  # confirm it matches what you intended
```

**Never `alembic stamp` to escape a failed migration** unless you have confirmed
by inspection that the schema genuinely matches the revision you are stamping.
Stamping is how you get a database that lies about its own state — and because
the container runs `upgrade head` at boot, a wrongly-stamped database will then
start up "successfully" with a schema the code cannot use.

### Rolling back across the purchase migrations

`e5f7a9b1c3d5` (purchases) and `f6a8b0c2d4e6` (purchase_notifications) both drop
their tables on downgrade. Going below `e5f7a9b1c3d5` **destroys every
entitlement record**, and users who paid will lose access until they restore.
Take the dump first, and prefer rolling the application back instead.

## 9. Secret rotation

Rotating `SECRET_KEY` invalidates every access and refresh token and signs out
every user. That is the correct response to a suspected key compromise; just
know it is user-visible. It does **not** affect purchases — entitlement lives in
the database, not in a token.

## Known limitations shipping with this deployment

- **Rate limiting is fail-open.** Any unexpected error, including a Redis
  connection blip, allows the request through (`app/core/rate_limit.py`). A
  Redis outage silently removes rate limiting rather than locking users out.
- **Single worker without Redis.** `start.sh` forces `--workers 1` when
  `REDIS_URL` is unset, because in-memory limits do not coordinate across
  processes.
- **Refunds are not instant** unless step 6 is configured.
- **No analytics**, so you are blind on onboarding drop-off by design.
- **Nothing here has run on real hardware or against real Apple infrastructure.**
